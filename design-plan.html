0. 왜 이 순서로 가는가

토큰을 먼저 고치고 원칙을 나중에 쓰면, 토큰이 곧 원칙이 되어버린다. "이미 이렇게 되어 있으니까"가 근거가 되고, 나중에 원칙을 바꾸려면 토큰을 또 갈아야 한다.

0-1. 이미 한 번 겪은 일

0-2. 이 프로젝트가 만드는 것

퍼블리싱 규약은 이미 .claude/rules/ 에 있다. 부족한 쪽은 디자인 체계이고, 그래서 외부 시스템(당근 SEED · Radix · Figma)의 결론을 근거로 빌려온다. 최종 목표는 디자인과 퍼블 규약이 둘 다 정해진 컴포넌트 라이브러리다. 기존 규칙 문서도 여기서 정한 대로 새로 쓴다.

1. "훅"이 뭐고 왜 문제인가

이 문서에 "훅"이라는 말이 계속 나온다. 이것부터 알아야 나머지가 읽힌다.

1-1. 먼저 — 왜 소비자를 못 이기나

CSS는 어느 규칙이 이길지 이 순서로 결정한다.

origin  →  importance  →  @layer  →  specificity(상세도)
                            ↑
                    상세도보다 먼저 본다

우리 스타일은 전부 @layer nui.components 안에 있고, 소비자가 그냥 쓴 CSS는 레이어 밖(unlayered)이다. 레이어 밖이 레이어 안을 항상 이긴다. 

/* 소비자 — 레이어 밖. 상세도 0-1-0 */
:root { --nui-button-min-height: 50px; }

/* 우리 — 레이어 안. 상세도를 아무리 올려도 진다 */
@layer nui.components {
  html body .nui-button.nui-button--small { min-height: 2.25rem; }
}

이건 버그가 아니라 우리가 원해서 만든 구조다. @layer 를 쓴 이유가 "소비자가 우리 스타일을 쉽게 덮게 하려고"였다. 다만 그 성질 때문에 우리가 뚫어둔 구멍도 우리가 못 막는다.

1-2. "훅"은 CSS 한 줄이다

/* 우리가 쓰는 SCSS */
min-width: #{hook("button-min-width", 7.5rem)};

/* 빌드된 CSS — 이게 전부다 */
min-width: var(--nui-button-min-width, 7.5rem);

var(이름, 기본값) = "손님이 이 이름으로 값을 적어뒀으면 그걸 쓰고, 안 적었으면 원래 값". 즉 훅은 우리가 미리 뚫어둔 구멍이다. 지금 44개 있다.

1-3. 진짜 문제 — 구멍 하나가 여러 자리에 뚫려 있다 ★

/* _button.scss — 이름이 세 곳 모두 같다 */
.nui-button         { min-height: var(--nui-button-min-height, 3.5rem);  }  /* 56px */
.nui-button--medium { min-height: var(--nui-button-min-height, 3rem);    }  /* 48px */
.nui-button--small  { min-height: var(--nui-button-min-height, 2.25rem); }  /* 36px */
/* 소비자 — 딱 한 줄 */
:root { --nui-button-min-height: 50px; }

세 자리가 전부 50px이 된다. 버튼의 크기 variant가 통째로 죽는다. 손잡이 하나가 S·M·L 세 개에 동시에 연결돼 있는 셈이고, 우리가 잘못 뚫은 것이다.

밑줄 변수는 창구가 아니라 variant를 구현하는 수단이다. .nui-button--primary 가 변수 하나만 갈아끼워 배경·테두리를 한꺼번에 바꾼다. 없애면 variant 자체가 불가능해진다. 공개 API가 아니므로 문서화하지 않고, 코드에는 그대로 남는다. 

.nui-button           { --nui-_button-main: var(--nui-action-neutral); }
.nui-button--primary  { --nui-_button-main: var(--nui-action-primary); }
.nui-button {
  background:   var(--nui-_button-main);
  border-color: var(--nui-_button-main);   /* 한 변수가 두 속성을 먹인다 */
}

2. 원칙 — 계층과 창구는 다른 축이다 ★

"SEED처럼 2계층"과 "컴포넌트별 변수를 연다"는 충돌하지 않는다. 둘은 다른 축이기 때문이다.

축 1 — 계층

값이 어디서 오는가

우리 내부의 문제다. 소비자는 알 필요가 없다.
action-primary 가 color-brand-9 에서 온다는 것.

축 2 — 창구

소비자가 어디를 만지는가

공개 API의 문제다. 한 번 열면 약속이 된다.
--nui-button-lg-height 를 덮어쓸 수 있다는 것.

SEED가 2계층인 것은 축 1의 이야기다. 그리고 SEED에는 축 2가 없다 — 사내 시스템이라 소비자가 덮어쓰는 시나리오를 상정하지 않기 때문이다. 우리는 npm 배포 라이브러리라 축 2가 반드시 필요하다.

2-1. 창구를 어디에 뚫나 — 한 문장 규칙

소비자가 잘못 바꿨을 때 자기 눈으로 알아챌 수 있으면 연다.
알아챌 수 없으면 막는다.

색은 짝이 있고, 깨진 게 안 보인다

/* 소비자가 버튼 배경만 연하게 바꾼다 */
:root { --nui-button-primary-bg: #a7e0d8; }

/* 글자색은 우리 것이 그대로 남는다 */
.nui-button--primary { color: var(--nui-action-primary-fg); }  /* 흰색 */

/*  결과 → 연한 배경 + 흰 글자 = 대비 1.3:1
    읽을 수 없다. 그런데 소비자는 모른다.               */

디자이너가 아니면 대비가 부족한지 눈으로 알기 어렵고, 저시력 사용자만 못 읽게 된다. 게다가 우리가 만든 글자색이 그대로 남아 있으니 절반은 우리 책임이다.

radius · 간격 · 크기 · 선 두께는 짝이 없다

:root { --nui-button-radius: 20px; }

/*  결과 → 버튼이 둥글어진다. 끝.
    마음에 안 들면 바로 보인다.  */

소비자가 스스로 판단할 수 있는 값은 막을 이유가 없다.

딱 하나 예외 — 포커스 링 두께

일반 테두리 border-width포커스 링 focus-width
역할요소의 외곽을 그린다 "지금 여기에 커서가 있다"를 알린다
잘못 바꾸면 굵거나 얇아 보인다. 바로 눈에 띈다 키보드 사용자만 포커스를 놓친다.
마우스로 쓰는 소비자는 알아채지 못한다
처분 연다 막는다

2-3. 훅 이름 규칙

--nui-{컴포넌트}-{옵션?}-{요소?}-{속성}

읽으면 문장이 된다 — "버튼의 lg 옵션의 높이" 

--nui-button-lg-height          버튼 · lg 옵션 · 높이
--nui-button-lg-padding-x       버튼 · lg 옵션 · 좌우 여백
--nui-button-sm-height          버튼 · sm 옵션 · 높이
--nui-button-round-radius       버튼 · round 옵션 · 둥글기

--nui-button-radius             버튼 · 둥글기            (옵션 없음)
--nui-button-border-width       버튼 · 테두리 두께        (옵션 없음)
--nui-accordion-header-gap      아코디언 · 헤더 · 간격    (요소 있음)

왜 옵션이 먼저인가

옵션별로 묶이기 때문이다. 소비자가 "lg 버튼을 통째로 손보고 싶다" 할 때 button-lg-* 로 한자리에 모인다. 

--nui-button-lg-height       ┐
--nui-button-lg-padding-x    ┘ lg 옵션의 스타일이 인접한다

--nui-button-sm-height       ┐
--nui-button-sm-padding-x    ┘ sm 옵션도 마찬가지

옵션이 없는 속성에는 옵션을 붙이지 않는다. border-width 는 컴포넌트당 하나뿐이므로 button-border-width 다. 있지도 않은 옵션을 이름에 넣지 않는다.

옵션 이름은 값의 크기 순서를 따른다

큰 것부터 lg · md · sm 이다. 소비자는 -sm 을 보고 "가장 작은 것"이라고 읽기 때문이다. 그리고 기본값은 언제나 md — 위아래로 lg 와 sm 이 있는 형태가 표준이다.

지금바뀐 뒤
Button 기본 56px (가장 크다) --large 56px 클래스 신설
--medium 48px 기본 48px 기본이 작아진다
--small 36px--small 36px
Popup --large 40rem그대로
기본 30rem (가운데)그대로 — 이미 md 다
--small 22.5rem그대로

Button은 시각 변경이 따라온다. 기본 버튼 높이가 56px → 48px 로 작아지고, 56px을 쓰려면 --large 를 명시해야 한다. 클래스가 늘어나므로 컴포넌트 API 변경이기도 하다.

지금 기본이 가장 큰 것은 원본 프로젝트에서 온 유산이고, "기본은 가운데"가 표준이라 여기서 바로잡는다.

2-4. 훅을 어디까지 여나

소비자가 이름을 보고 "아, 그 부분" 하고 떠올릴 수 있는 자리만 연다.

연다열지 않는다
기준 컴포넌트 안쪽 — 자기가 소유한 것 컴포넌트 바깥 — 부모가 소유한 것
속성 padding gap border-radius border-width height min-height min-width
자기 치수(width — Switch·Popup 등)		 margin position display flex-direction order z-index
블록 요소의 width
+ 색 전부 · 포커스 링 두께
자리 컴포넌트 본체
구조적 요소 — head · body · foot
크기 variant — lg · md · sm		 값이 0 인 자리
variant override — 원본 훅을 따라온다
내부 배치용 — positioner · wrapper

왜 이 기준이 필요한가 — 컴포넌트가 쓰는 속성 자리를 전부 세면 145개다(padding 47 · gap 16 · height 51 · radius 31). 전부 열면 소비자가 뭘 써야 할지 못 찾는다. 그런데 실제로 열어보면 대부분이 열 필요 없는 자리다. 

Popup 의 padding 14자리
  __head / __body / __foot        ← 의미 있다 (3개)
  __close  padding: 0             ← 0이다
  --bottom-sheet / --full / ...   ← variant override. 원본 훅을 따라온다

이 기준이면 컴포넌트당 3~6개 · 전체 40~70개가 된다. 부족하면 나중에 추가하면 되고, 훅을 여는 것은 non-breaking 이라 나중이 비싸지 않다. 반대로 열었다 닫는 것은 breaking 이므로 적게 열고 시작한다.

겹친 이름이 전부 나쁜 건 아니다. selector-size 는 두 자리에 쓰이지만 쪼개면 안 된다 — Checkbox·Radio의 width 와 height 를 같은 값으로 묶어 정사각형을 보장하는 자리이기 때문이다. 같은 이유로 한 컴포넌트 안의 테두리 두께도 하나로 묶는다. "의도해서 묶은 것"과 "실수로 겹친 것"을 구분해야 한다.

2-5. !important 는 필요 없다

1-1의 @layer 때문에 소비자는 !important 없이도 이긴다. 문서 사이트에서 실제로 재봤다. 

getComputedStyle(btn).borderRadius;        // → "4px"   우리 값

// 소비자 CSS를 흉내낸다. !important 없음, 상세도도 같음
style.textContent = '.nui-button { border-radius: 0px; }';
document.head.appendChild(style);

getComputedStyle(btn).borderRadius;        // → "0px"   소비자가 이겼다

오히려 !important 를 쓰면 자기 발등을 찍는다.

.my-button { border-radius: 0 !important; }
.my-button:hover { border-radius: 4px; }   /* ← 자기 규칙인데 안 먹는다 */

보통의 라이브러리는 !important 없이 못 덮는 경우가 많아 소비자가 습관적으로 붙인다. "우리는 !important 없이 덮인다"를 README와 Foundations에 명시한다.

2-6. 규칙은 기계가 지킨다 ★

여기까지가 원칙이다. 그런데 원칙을 문서에만 두면 다시 어긋난다. 0-1의 hover 배경 3종이 정확히 그렇게 생겼다 — 규칙이 없어서가 아니라 규칙을 지켰는지 아무도 확인하지 않아서다.

맞춤법 검사기와 같다. "이렇게 쓰세요"라고 적어두는 것과, 잘못 쓰면 빨간 줄이 그어지는 것은 다르다.

이미 있는 파일이다

packages/ui/scripts/check-token-layers.mjs      ← 검사 스크립트
npm run verify:tokens                            ← 이걸로 실행된다

// 배포 전 품질 게이트에 이미 물려 있다
npm run verify  =  verify:css + verify:tokens + publint + attw

SCSS 파일들을 읽어서 규칙을 어긴 곳을 찾고, 있으면 빌드를 실패시킨다. 빌드된 CSS 가 아니라 소스를 읽는데, 어떤 토큰 이름을 참조했는지는 컴파일 뒤에 알 수 없기 때문이다.

5-3. pressed 배율

/* before — 매직 넘버 */
.nui-button:active { transform: translateY(1px); }

/* after — 크기별 축소 배율 */
--nui-scale-95: 0.95;   /* 작은 요소 — 칩 · 아이콘 버튼 */
--nui-scale-97: 0.97;   /* 중간 */
--nui-scale-98: 0.98;   /* 큰 요소 — 전면 버튼 · 카드 */

왜 세 단계인가 — 큰 요소일수록 덜 줄여야 같은 정도로 눌린 느낌이 난다. 전면 버튼을 0.95로 줄이면 과하게 움츠러들고, 작은 칩을 0.98로 줄이면 티가 안 난다.

이번 범위에서는 토큰만 만든다. translateY → scale 로 실제 표현을 바꾸는 것은 시각 변경이라 컴포넌트 단계(4단계)에서 한다. 토큰이 먼저 있어야 그때 일괄로 바꿀 수 있다.

6-2. 검증 — 무엇으로 "제대로 됐다"고 하나

성공 기준은 하나다 — 이름만 바뀌고 화면은 그대로. 의도된 예외는 둘이다 — 선 색 위계 교정과 Button 기본 높이(56→48px).

단계방법통과 기준
1. 기계 검사 npm run typecheck · npm run verify 전부 통과. 새 검사 규칙도 통과
2. 빌드 npm run build:ui · build:docs에러 0
3. CSS 시각 회귀 ★ 빌드된 styles/*.css 를 변경 전후로 비교한다. 토큰 이름을 원래대로 되돌리는 치환을 걸면 diff 가 0이어야 한다 값 변화 0건
의도된 변경 두 가지는 예외 — 선 색 위계(border-divider·border-section)와 Button 기본 높이 56→48px. 예상 diff 를 미리 적어두고 대조한다
4. 브라우저 문서 사이트 전 페이지 × 라이트/다크 · verify:console 콘솔 에러·경고 0
5. 동작 회귀 verify:select-rhf · verify:datepicker · verify:a11y 전부 통과
6. 훅 대조 빌드된 CSS의 훅 이름을 전부 뽑아 5-2 목록과 1:1 대조 목록에 없는 훅 0 · 목록에 있는데 없는 훅 0

3번이 핵심 검증이다. "화면이 안 바뀐다"는 주장을 기계가 확인해준다. 눈으로 보는 것보다 확실하고, 빠뜨린 자리도 잡아낸다.

6-4. 작업 순서

  1. _seed.scss — 토큰 먼저. 컴포넌트가 참조할 것이 있어야 한다
  2. 검사 스크립트 완료 — 새 규칙을 먼저 넣으면 이후 작업이 자동으로 검사된다
  3. 컴포넌트 SCSS — 파일 단위로. 한 파일 끝날 때마다 CSS diff 확인
  4. rules/ 문서 — 코드가 확정된 뒤에 쓴다
  5. Foundations 페이지
  6. changeset + 전체 검증

2번을 3번보다 먼저 하는 것이 요령이다. 검사 규칙을 먼저 넣으면 컴포넌트를 고치는 동안 실수가 즉시 잡힌다. 나중에 넣으면 다 고치고 나서 한꺼번에 터진다.
