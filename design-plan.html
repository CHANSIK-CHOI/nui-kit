범위 밖

0-2. 이 프로젝트가 만드는 것

퍼블리싱 규약은 이미 .claude/rules/ 에 있다. 부족한 쪽은 디자인 체계이고, 그래서 외부 시스템(당근 SEED · Radix · Figma)의 결론을 근거로 빌려온다. 최종 목표는 디자인과 퍼블 규약이 둘 다 정해진 컴포넌트 라이브러리다. 기존 규칙 문서(rules/)도 여기서 정하는 대로 새로 쓴다.

1. "훅"이 뭐고 왜 문제인가

이 문서에 "훅"이라는 말이 계속 나온다. 나머지를 읽으려면 이것부터 알아야 하므로 먼저 설명한다. 결론만 말하면 훅은 CSS var() 한 줄이고, 지금 31개 있고, 그중 일부가 고장 나 있다.

1-1. 먼저 — 왜 소비자를 못 이기나

이 문서 전체를 관통하는 전제다. CSS는 어느 규칙이 이길지 이 순서로 결정한다.

origin  →  importance  →  @layer  →  specificity(상세도)
                            ↑
                    상세도보다 먼저 본다

우리 스타일은 전부 @layer nui.components 안에 있고, 소비자가 그냥 쓴 CSS는 레이어 밖(unlayered)이다. 레이어 밖이 레이어 안을 항상 이긴다. 상세도는 그 다음에야 본다. 

/* 소비자 — 레이어 밖. 상세도 0-1-0 */
:root { --nui-button-min-height: 50px; }

/* 우리 — 레이어 안. 상세도를 아무리 올려도 진다 */
@layer nui.components {
  html body .nui-button.nui-button--small { min-height: 2.25rem; }
}

이건 버그가 아니라 우리가 원해서 만든 구조다. @layer 를 쓴 이유가 "소비자가 우리 스타일을 쉽게 덮게 하려고"였다. 다만 그 성질 때문에 우리가 뚫어둔 구멍도 우리가 못 막는다.

1-2. "훅"이 대체 뭔가

/* 우리가 쓰는 SCSS */
min-width: #{hook("button-min-width", 7.5rem)};

/* 빌드된 CSS — 이게 전부다 */
min-width: var(--nui-button-min-width, 7.5rem);

var(이름, 기본값) = "손님이 이 이름으로 값을 적어뒀으면 그걸 쓰고, 안 적었으면 원래 값". 즉 훅은 우리가 미리 뚫어둔 구멍이다. 지금 31개 있다.

1-3. 진짜 문제 — 구멍 하나가 여러 자리에 뚫려 있다 ★

/* _button.scss — 이름이 세 곳 모두 같다 */
.nui-button         { min-height: var(--nui-button-min-height, 3.5rem);  }  /* 56px */
.nui-button--medium { min-height: var(--nui-button-min-height, 3rem);    }  /* 48px */
.nui-button--small  { min-height: var(--nui-button-min-height, 2.25rem); }  /* 36px */
/* 소비자 — 딱 한 줄 */
:root { --nui-button-min-height: 50px; }

세 자리가 전부 50px이 된다. 버튼의 크기 variant가 통째로 죽는다. 손잡이 하나가 S·M·L 세 개에 동시에 연결돼 있는 셈이고, 우리가 잘못 뚫은 것이다.

짝이 있다
모양 (radius)8 accordion-radius button-radius popup-radius select-radius textarea-radius textfield-radius toast-radius tooltip-radius 쪼개고 확장

--nui-_* 내부 배선 9개는 이것과 별개다.

밑줄 변수는 창구가 아니라 variant를 구현하는 수단이다. .nui-button--primary 가 --nui-_button-main 하나만 갈아끼워 배경·테두리를 한꺼번에 바꾼다. 없애면 variant 자체가 불가능해진다. 공개 API가 아니므로 문서화하지 않고, 코드에는 그대로 남는다.

2. 토큰 체계의 두 축 — 계층 ≠ 창구 ★

당신이 짚은 것

"뭔가 우리가 SEED처럼 토큰 체계를 정리하려고 하는 것에서 조금씩 무너지는 것 같은데 컴포넌트도 그렇고 이 선도 그렇고 한번 검토해줘"

정확한 지적이고, 검토 결과는 "무너지는 게 아니라 두 가지를 섞어 봤다"이다. 지금까지 나는 "계층"과 "창구"를 한 덩어리로 말했는데, 이 둘은 다른 축이다. 나눠 놓으면 색·치수·선이 전부 한 규칙으로 설명된다.

축 1 — 계층

값이 어디서 오는가

우리 내부의 문제다. 소비자는 알 필요가 없다.
action-primary 가 color-brand-9 에서 온다는 것.

축 2 — 창구

소비자가 어디를 만지는가

공개 API의 문제다. 한 번 열면 약속이 된다.
--nui-button-height-sm 을 덮어쓸 수 있다는 것.

SEED가 2계층인 것은 축 1의 이야기다. 그리고 SEED에는 축 2가 아예 없다 — 사내 시스템이라 소비자가 덮어쓰는 시나리오를 상정하지 않기 때문이다. 우리는 npm 배포 라이브러리라 축 2가 반드시 필요하다. 그러니 "SEED처럼 2계층"과 "컴포넌트별 변수를 연다"는 충돌하지 않는다. 다른 축이다.

2-1. 그럼 창구는 어디에 뚫나 — 한 문장 규칙

값이 다른 값의 근거가 되면 위에서만 연다. 독립적이면 개별로 연다.

이걸 연쇄라고 부르자. 색과 치수는 연쇄하는 정도가 완전히 다르다.

색은 연쇄한다 — 실측했다

primitive 색 하나가 semantic 몇 개로 퍼지는지 세어봤다. 

--nui-color-gray-12  →  5개로 퍼진다
                        text-primary · layer-inverse · control-text
                        control-icon-strong · action-neutral

--nui-color-gray-6   →  4개
                        border-default · control-border-disabled
                        control-track · action-border-disabled

--nui-color-brand-9  →  2개
                        control-accent · action-primary

그리고 이 semantic들이 다시 컴포넌트 수십 곳으로 퍼진다. 즉 색은 하나를 건드리면 화면 전체가 흔들린다.

그래서 색을 컴포넌트별로 열면 연쇄가 끊긴다. 버튼 배경만 연한 색으로 바꾸면 글자색은 따라오지 않아 대비가 깨진다. 색의 창구는 위쪽 하나여야 한다.

치수는 연쇄하지 않는다

Button 높이를 40px로 바꾸면 무엇이 따라 바뀌나? 아무것도 안 바뀐다. Popup 너비도, Tooltip 여백도 그대로다. 그리고 아무것도 깨지지 않는다.

space-4(16px)는 space-4일 뿐이고, 테마를 바꿔도 16px이다. 그래서 치수에는 역할 계층 자체가 없다 — 이름이 곧 역할이다. 연쇄가 없으니 개별로 열어도 안전하다.

2-2. 그럼 무엇을 막고 무엇을 여나 ★

당신의 결정

"선 컬러·두께는 브랜드 컬러와 같이 컴포넌트에서 변경하지 못하도록. radius 는 막지 말고 열자 — 어떻게 보면 모양에 관한 거니까 컴포넌트 수정하는 것에 포함하는 게 맞을 것 같다"

훅 31개를 성격별로 세어보면 이렇게 갈린다.

성격개수예처분
색11 button-bg tooltip-bg textfield-border-color 막는다
모양 (radius)8 button-radius popup-radius tooltip-radius 연다
간격2 accordion-gap button-padding-x 연다
크기10 button-min-height popup-width switch-width 연다

색 11개만 막고 나머지 20개는 연다. 그 경계의 근거가 이것이다.

소비자가 잘못 바꿨을 때 자기 눈으로 알아챌 수 있으면 연다.
알아챌 수 없으면 막는다.

"짝이 있느냐"보다 이게 정확하다. 색을 막는 진짜 이유는 짝이 있어서가 아니라, 짝이 깨진 걸 소비자가 모르기 때문이다.

색만 "짝"이 있다 — 그리고 깨진 게 안 보인다

색은 배경과 글자가 한 쌍이다. 둘의 관계가 읽을 수 있는지를 결정한다. 그런데 우리 훅은 배경만 열어놨다. 

/* 소비자가 버튼 배경만 연하게 바꾼다 */
:root { --nui-button-primary-bg: #a7e0d8; }

/* 글자색은 우리 것이 그대로 남는다 */
.nui-button--primary { color: var(--nui-action-primary-fg); }  /* 흰색 */

/*  결과 → 연한 배경 + 흰 글자 = 대비 1.3:1
    읽을 수 없다. 그런데 소비자는 모른다.               */

이게 "보이지 않게 깨지는" 경우다. 디자이너가 아니면 대비가 부족한지 눈으로 알기 어렵고, 저시력 사용자만 못 읽게 된다. 게다가 우리가 만든 글자색이 그대로 남아 있으니 절반은 우리 책임이다.

radius · 간격 · 크기는 짝이 없다

/* 소비자가 버튼을 둥글게 바꾼다 */
:root { --nui-button-radius: 20px; }

/*  결과 → 버튼이 둥글어진다. 끝.
    같이 바꿔야 할 다른 값이 없다.
    마음에 안 들면 바로 보인다.                        */

바꾸면 바로 눈에 보이고, 그게 전부다. "버튼만 알약 모양"이 마음에 들면 그게 정답이고, 이상하면 바로 알아채고 되돌린다. 소비자가 스스로 판단할 수 있는 값은 막을 이유가 없다.

2-3. 선 두께는? — 열되, 포커스 링만 뺀다 ★

당신의 질문

"그렇게 치면 선 두께도 열어야 하나? 선 색상은 닫되?"

기준을 대면 열어야 한다. 선 두께를 2px로 바꾸면 바로 눈에 보인다. 같이 바꿔야 할 짝도 없다. 다만 딱 하나 예외가 있다.

먼저 — 지금 두께가 어떻게 쓰이는지 재봤다

토큰값자리쓰이는 곳
border-width1px17 Accordion 4 · Popup 3 · Datepicker 3 · Select 3 · Button · Choice · Textfield · Textarea
focus-width2px3 포커스 시 Textfield · Textarea · Select 의 테두리가 두꺼워진다
 
/* _textfield.scss — 포커스가 들어오면 테두리가 굵어진다 */
.nui-textfield:focus-within .nui-textfield__wrap {
  border-width: var(--nui-focus-width);   /* 1px → 2px */
}

그래서 두께는 두 종류다 — 성격이 다르다

일반 테두리 border-width포커스 링 focus-width
역할요소의 외곽을 그린다 "지금 여기에 커서가 있다"를 알린다
잘못 바꾸면 테두리가 굵거나 얇아 보인다.
바로 눈에 띈다		 키보드 사용자만 포커스를 놓친다.
마우스로 쓰는 소비자는 알아채지 못한다
기준 적용 연다 막는다

포커스 링이 색과 같은 성격이다. 대비가 부족한 것도, 포커스 링이 안 보이는 것도 일부 사용자만 겪고 소비자는 모른다. WCAG 2.4.11(Focus Appearance)이 포커스 표시의 최소 크기를 요구하는 이유이기도 하다.

그래서 이렇게 정리된다

/* PRIMITIVE — 전역 두께 스케일. 여기는 소비자가 덮을 수 있다 */
--nui-border-width-1: 1px;
--nui-border-width-2: 2px;

/* 컴포넌트 훅 — 새로 연다. border 를 쓰는 8개 컴포넌트 */
--nui-button-border-width      --nui-popup-border-width
--nui-textfield-border-width   --nui-textarea-border-width
--nui-select-border-width      --nui-accordion-border-width
--nui-datepicker-border-width  --nui-checkbox-border-width

/* 포커스 링 — 훅 없음. 접근성 요소다 */
--nui-focus-width: 2px;        /* 전역에서만 조정 가능 */

훅은 "그 컴포넌트가 실제로 쓰는 속성"에만 만든다. Toast나 Tooltip은 border 를 쓰지 않으므로 두께 훅도 만들지 않는다. 안 쓰는 훅은 죽은 토큰이 된다.

덤으로 찾은 것 — Accordion에 2px 하드코딩이 있다. _accordion.scss:160 인데, 확인해보니 테두리가 아니라 화살표 아이콘이었다 (border-right + border-bottom + rotate(45deg) 로 V자를 그린다). 선이 아니라 도형을 그리는 수단이므로 두께 토큰 대상이 아니다. 다만 이런 자리가 더 있는지는 2단계에서 훑는다.

2-4. 이름 규칙 — 속성이 먼저, variant가 뒤 ★

당신의 제안

"여는 것은 컴포넌트처럼 button-lg-line-size, button-lg-radius 이렇게"

방향은 같은데 순서를 뒤집는 쪽을 권한다. 이유가 하나 있다 — variant 축이 속성마다 다르기 때문이다.

속성이 속성의 variant 축
height · padding-xlg / md / sm — 크기
radius기본 / round — 모양
border-width없다 — 하나뿐

variant를 앞에 두면 존재하지 않는 조합이 만들어진다. 

/* variant 먼저 — button-lg-radius 는 무엇인가? */
--nui-button-lg-height         ✓
--nui-button-lg-radius         ✗ radius 는 lg/md/sm 축이 아니다
--nui-button-lg-border-width   ✗ border-width 는 variant 가 없다

/* 속성 먼저 — 속성이 정해지면 그 다음에 올 variant 가 결정된다 */
--nui-button-height-lg    --nui-button-height-md    --nui-button-height-sm
--nui-button-radius       --nui-button-radius-round
--nui-button-border-width

규칙

속성 이름은 CSS 속성명을 그대로 쓴다. line-size 보다 border-width 가 낫다 — 소비자가 CSS를 보고 바로 어떤 토큰을 찾을지 알 수 있고, 우리 전역 토큰(--nui-border-width-1)과도 이름이 이어진다.

radius를 열 때 문서에 적어둘 것

지금 컴포넌트마다 radius 값이 다르고 그건 의도된 것이다 — 요소가 클수록 더 둥글어야 같은 정도로 둥글어 보인다. 

Button    radius-1  (4px)   ← 작고 각지다
Tooltip   radius-3  (12px)
Popup     radius-6  (24px)  ← 크고 둥글다

전체를 둥글게 하고 싶으면 전역 스케일을 덮는 쪽이 낫다 — 비율이 유지된다. 컴포넌트별 훅은 "이것만 다르게"일 때 쓴다. 둘 다 열어두고 문서에서 안내한다. 

/* 권장 — 전체가 비율을 유지한 채 둥글어진다 */
:root { --nui-radius-1: 8px; --nui-radius-3: 16px; --nui-radius-6: 32px; }

/* 이것만 다르게 */
:root { --nui-button-radius: 999px; }

2-5. !important 는 필요 없다 — 실측했다 ★

당신의 제안

"속성 중에 radius를 없애는 건 CSS에서 0 !important 로 못박고"

!important 없이도 소비자가 이긴다. 1-1에서 설명한 @layer 때문인데, 말로만 하면 믿기 어려우니 실제 문서 사이트에서 재봤다. 

// 브라우저에서 실행한 코드
const btn = document.querySelector('.nui-button');
getComputedStyle(btn).borderRadius;        // → "4px"   우리 값

// 소비자가 레이어 밖에 쓴 CSS를 흉내낸다. !important 없음
const style = document.createElement('style');
style.textContent = '.nui-button { border-radius: 0px; }';
document.head.appendChild(style);

getComputedStyle(btn).borderRadius;        // → "0px"   소비자가 이겼다

4px → 0px. 상세도도 같고 !important 도 없는데 소비자 규칙이 이겼다. 우리 규칙이 @layer nui.components 안에 있고 소비자 규칙은 밖에 있기 때문이다. 캐스케이드가 상세도보다 레이어를 먼저 보기 때문에 생기는 결과다.

오히려 !important 를 쓰면 손해다

/* 소비자가 이렇게 쓰면 */
.my-button { border-radius: 0 !important; }

/* 자기 자신의 다음 규칙도 못 덮는다 */
.my-button:hover { border-radius: 4px; }        /* ← 안 먹는다 */
.my-button.is-featured { border-radius: 12px; } /* ← 안 먹는다 */

!important 는 자기 발등을 찍는다. 나중에 그 컴포넌트를 조건부로 다르게 하고 싶어지면 또 !important 를 붙여야 하고, 그렇게 계단이 쌓인다.

이건 문서에 적어둘 가치가 있다. 보통의 라이브러리는 !important 없이 못 덮는 경우가 많아서 소비자가 습관적으로 붙인다. "우리 라이브러리는 !important 없이 덮인다"를 README와 Foundations에 명시하면 소비자가 불필요한 !important 를 쌓지 않는다.

2-7. 선(stroke)에 적용해보면 ★

선은 다른 것과 다르다. 색과 두께를 둘 다 갖기 때문이다. 그래서 "Primitive에 넣나 Semantic에 넣나"가 헷갈렸던 것인데, 두 개를 따로 떼어 놓고 규칙을 대면 깨끗하게 갈린다.

선 색선 두께
연쇄하나 한다. border-default 는 gray-6 에서 오는데, 그 gray-6 은 다른 3개와 함께 쓴다 안 한다. 1px은 그냥 1px이다
계층 Primitive(gray 스케일) → Semantic(역할) Primitive만
창구 브랜드 색 생성 + semantic 덮어쓰기 컴포넌트별 변수 가능
SEED의 3분할 여기에 해당한다. 전부 색 토큰이다 해당 없음

그래서 당신의 제안이 맞다. 다만 짚어둘 게 하나 있다.

SEED의 3분할은 "두께"가 아니라 "색"이다. stroke.neutral-weak · -subtle · -muted 세 개는 전부 색 토큰이고, 나누는 기준은 굵기가 아니라 "한 화면에 몇 번 등장하는가"다. 그러니 말씀하신 대로 두께는 Primitive, 색은 Semantic 으로 두 축을 다 만들면 된다.

문제 ① 같은 "형태선"인데 값이 두 개다

형태선은 요소의 외곽을 그리는 선이다 — 카드, 인풋, 아웃라인 버튼의 테두리. 그런데 우리는 두 가지 다른 값을 쓰고 있다. 

/* Popup 카드의 외곽 */
border: 1px solid var(--nui-border-default);    /* gray-6 */

/* Textfield 의 외곽 */
border: 1px solid var(--nui-control-border);    /* gray-7  ← 더 진하다 */

다행히 이건 문제가 아닐 수도 있다. Radix 12단계에서 6은 "비상호작용 테두리", 7은 "상호작용 테두리"다. 즉 누를 수 있는 것과 가만히 있는 것을 색 진하기로 구분하는 것이고, 이미 그 규칙대로 되어 있다. 다만 이름이 그걸 말해주지 않는다 — border-default 와 control-border 라는 이름만 보고 "왜 값이 다르지?"를 알 수 없다.

문제 ② 반복항목 구분선이 입력 컨트롤 토큰을 빌려 쓰고 있다 ⚠️

Accordion의 line 스타일은 항목들이 세로로 쌓이고 그 사이를 선이 나눈다. 전형적인 반복항목 구분선이다. 그런데 코드를 보면 — 

/* _accordion.scss:46 — Accordion line variant 의 항목 구분선 */
.nui-accordion--line .nui-accordion__item {
  border-bottom: 1px solid var(--nui-control-border);
                                  ↑
                     입력 컨트롤(Textfield·Select) 전용 토큰이다

Accordion 항목은 입력 컨트롤이 아니다. 그런데 "구분선용 토큰"이 없으니 가장 그럴듯한 걸 빌려 쓴 것이다. 이게 정확히 hover 배경 3종과 같은 형태의 문제다 — 토큰이 없어서가 아니라 "이럴 때 뭘 쓴다"가 없어서 벌어진다.

왜 이게 나중에 터지나 — 언젠가 control-border 의 값을 바꿔야 할 일이 생긴다(입력 테두리가 너무 연하다 같은 이유로). 그러면 아무 상관 없는 Accordion 구분선이 같이 바뀐다. 그때는 왜 바뀌는지 찾기도 어렵다.

구분선·경계선에 alpha(gray-a3 a4)를 제안하는 이유 — SEED도 이 둘만 alpha를 쓴다. 구분선은 어떤 배경 위에 놓일지 모르기 때문이다. 흰 카드 위일 수도, 회색 패널 위일 수도 있다. 불투명 회색이면 배경에 따라 튀지만 반투명이면 아래 색과 섞여 어디서든 자연스럽다. 우리에겐 이미 gray-a3 ~ a7 이 있다.

4-3. D-05 치수 훅 — 쪼개고, 전 컴포넌트로 확장

당신의 답

"버튼뿐만 아니라 모든 컴포넌트의 간격·패딩 등 각 요소별로 변수명으로 쪼개서 커스텀할 수 있도록. 다만 레이아웃은 변경 못 하게, 각 컴포넌트의 디테일한 스타일만 수정하도록"

① 겹친 이름을 쪼갠다

/* ── before — 세 자리가 한 이름을 공유한다 ──────── */
.nui-button         { min-height: var(--nui-button-min-height, 3.5rem);  }
.nui-button--medium { min-height: var(--nui-button-min-height, 3rem);    }

D-04로 색 훅 11개가 빠지고 20개가 남는다 (radius 8 · 간격 2 · 크기 10). 그중 이름이 겹치는 것은 4개다. 세어봤다.

겹친 이름이 전부 나쁜 건 아니다. selector-size 도 두 자리에 쓰이는데 이건 쪼개면 안 된다 — Checkbox·Radio의 width 와 height 를 같은 값으로 묶어 정사각형을 보장하는 자리이기 때문이다. 쪼개면 소비자가 한쪽만 바꿔 타원이 될 수 있다. "의도해서 묶은 것"과 "실수로 겹친 것"을 구분해야 한다. 

.nui-checkbox, .nui-radio {

  height: var(--nui-selector-size, 1.375rem);   /* 같은 이름이어야 정사각형 */
}

"레이아웃은 안 되고 디테일만"이라는 기준을 규칙으로 못박아야 나중에 훅을 추가할 때 다시 고민하지 않는다. 이렇게 나눈다.

연다닫는다
기준 컴포넌트 안쪽 — 자기가 소유한 것 컴포넌트 바깥 — 부모가 소유한 것
속성 padding gap border-radius height min-height min-width
자기 치수(width — Switch·Popup 등)		 margin position display flex-direction order z-index

왜 바꿔도 그 컴포넌트 안에서 끝난다 바꾸면 주변 배치가 깨진다. margin 으로 바깥 간격을 만들지 않는다는 현행 원칙과도 맞는다

왜 width 가 양쪽에 있나 — Switch(46×26px)나 Popup처럼 자기 치수를 갖는 컴포넌트의 폭은 자기 것이다. 반면 Textfield·Button처럼 부모 폭을 채우는 블록 요소의 폭은 부모 것이다. 전자는 열고 후자는 닫는다.

4-6. D-07 pressed 배율을 토큰으로

/* ── before — 매직 넘버 ──────────────────────── */
.nui-button:active { transform: translateY(1px); }

/* ── after — SEED 방식. 크기별 축소 배율 ──────── */
--nui-scale-95: 0.95;   /* 작은 요소 — 칩 · 아이콘 버튼 */
--nui-scale-97: 0.97;   /* 중간 */
--nui-scale-98: 0.98;   /* 큰 요소 — 전면 버튼 · 카드 */

.nui-button:active { transform: scale(var(--nui-scale-98)); }

왜 세 단계인가 — 큰 요소일수록 덜 줄여야 같은 정도로 눌린 느낌이 난다. 전면 버튼을 0.95로 줄이면 과하게 움츠러들고, 작은 칩을 0.98로 줄이면 티가 안 난다.

이번 범위에서는 토큰만 만든다. translateY → scale 로 실제 표현을 바꾸는 것은 시각 변경이라 컴포넌트 단계(4단계)에서 한다. 토큰이 먼저 있어야 그때 일괄로 바꿀 수 있다.

4-7. D-09 -static 과 html { font-size: 10px }

당신의 답

"SEED처럼 -static 을 도입하고 싶다. html 에 font-size 10px 넣는 건 빌드 시점에 스크립트로 넣을 수 있으면 그렇게 하고, 이후 브레이크포인트별 html font-size 수정은 소비자에게 맡기자"

세 가지를 나눠서 답한다. 둘은 되고 하나는 안 된다.

① -static 도입 — 가능

font-size 토큰마다 px 짝을 만든다. 이름에 static 이 박혀 있어 "여기는 의도적으로 고정했다"가 검색된다. 

--nui-font-size-4:         1rem;    /* 기본 — 사용자 글꼴 설정을 따른다 */
--nui-font-size-4-static:  16px;    /* 예외 — 고정. Switch 내부 텍스트 등 */

우리는 SEED보다 적게 만들면 된다. SEED는 크기·행간을 둘 다 두 벌로 갖는데, 우리 line-height 는 배수(1.5 같은 단위 없는 숫자)라 글꼴이 커져도 비율이 유지된다. letter-spacing 도 em 이라 마찬가지다. font-size 7개만 두 벌 = +7개로 끝난다.

② 브레이크포인트별 html font-size 조정 — 이미 가능

소비자가 이렇게 쓰면 우리 컴포넌트가 통째로 스케일된다. 우리가 이미 rem을 쓰고 있으므로 아무것도 안 해도 된다. 

/* 소비자 프로젝트 */
@media (min-width: 1440px) { html { font-size: 112.5%; } }  /* 18px 기준 */
@media (max-width: 480px)  { html { font-size: 87.5%;  } }  /* 14px 기준 */

③ 우리가 html { font-size: 10px } 를 배포 — 불가

세 가지 이유로 막힌다.

문제
1원칙 위반 html 은 전역 셀렉터다. 우리가 이걸 배포하면 소비자 프로젝트의 모든 rem이 함께 바뀐다. 소비자가 2rem 으로 써둔 곳이 32px → 20px로 줄어든다. "소비자 스타일을 오염시키지 않는다"는 우리 1원칙의 정면 위반이다
기계 검사에 걸린다 verify:css 가 "preflight.css 외 파일의 태그 셀렉터"를 실패로 잡는다. 지금 있는 검사다
강제 의존이 생긴다 우리 값을 10px 기준으로 다시 계산하면(예: 36px = 3.6rem), 소비자가 반드시 10px을 넣어야만 컴포넌트가 정상으로 보인다. 안 넣으면 전부 1.6배로 커진다. "설치하면 그냥 동작한다"가 깨진다

그리고 10px 은 접근성에서도 62.5% 보다 나쁘다

font-size: 10pxfont-size: 62.5%
사용자가 브라우저 글꼴을 20px로 키우면 무시된다. 10px 고정 12.5px로 따라 커진다
WCAG 1.4.4 (텍스트 200% 확대) 위반 통과
당신의 결정

"-static 사용하도록 할게"

정리 — 원하시는 것은 ③ 없이도 전부 된다

  • -static 도입 확정 font-size 7개만 두 벌 = +7개
  • 브레이크포인트별 스케일 → 소비자가 html font-size만 조정하면 된다. 지금도 되고, 문서에 방법을 적으면 끝난다
  • 10px 기준 → 하지 않는다. 얻는 것은 계산 편의뿐인데 1원칙 · 기계 검사 · 접근성 셋 다 잃는다

확정된 것 — 토큰 7개

--nui-font-size-1-static:  12px      --nui-font-size-5-static:  18px
--nui-font-size-2-static:  13px      --nui-font-size-6-static:  20px
--nui-font-size-3-static:  14px      --nui-font-size-8-static:  32px
--nui-font-size-4-static:  16px

어디에 쓸지는 아직 실측하지 않았다. 후보는 Switch(46×26px) · Checkbox(22×22px)처럼 자기 치수가 고정된 컨트롤의 내부 텍스트다. 글꼴 200%에서 실제로 깨지는지 브라우저로 확인한 뒤 대상 목록을 확정한다. 토큰은 이번에 만들고, 적용은 컴포넌트 단계(4단계)에서 한다. 실측에서 쓸 자리가 하나도 없으면 토큰도 만들지 않는다 — 죽은 토큰이 되므로.

9-1. 착수 전에 판단해야 하는 것 4가지 ★

계약을 쓰려고 코드를 전량 훑다가 기계적으로 처리하면 틀리는 자리 넷을 찾았다. 이걸 먼저 정하지 않으면 잘못 고친다.

함정 ① Button과 Popup의 크기 축이 다르다 ⚠️

/* Button — 기본이 가장 크다 */
.nui-button           min-height: size-field       56px  ← 기본
.nui-button--medium   min-height: size-control-xl  48px
.nui-button--small    min-height: size-control-md  36px

/* Popup — 기본이 가운데다 */
.nui-popup__panel              width: 30rem    ← 기본
.nui-popup--small  __panel     width: 22.5rem
.nui-popup--large  __panel     width: 40rem

둘 다 3단계인데 기본의 위치가 다르다. 기계적으로 -lg/-md/-sm 을 붙이면 어긋난다.

자리ButtonPopup
기본(클래스 이름 없음)button-height-lgpopup-width-md
--medium / (없음)button-height-md—
--smallbutton-height-smpopup-width-sm
(없음) / --large—popup-width-lg

결정 — 클래스가 아니라 실제 크기 순서를 따른다. Button 기본은 가장 크니까 -lg, Popup 기본은 가운데니까 -md. 소비자가 값을 보고 이름을 예측할 수 있어야 하기 때문이다.

함정 ② 한 컴포넌트에 border-width 가 여러 자리다

_accordion.scss   4자리 (22 · 34 · 46 · 177행)
_popup.scss       3자리 (46 · 94 · 135행)
_datepicker.scss  3자리 (38 · 130 · 262행)
_select.scss      3자리 (35 · 149 · 206행)
나머지 4개 파일    각 1자리

이건 쪼개지 않는다. selector-size 와 같은 이유다 — 한 컴포넌트 안의 테두리는 같은 두께여야 자연스럽다. Accordion 헤더는 1px인데 항목 구분선만 2px이면 어긋나 보인다. "의도해서 묶은 것"이므로 컴포넌트당 훅 하나다.

함정 ③ transparent 테두리가 있다

_popup.scss:94        border: var(--nui-border-width) solid transparent;
_datepicker.scss:262  border: var(--nui-border-width) solid transparent;

보이지 않는 테두리다. 왜 있냐면 — 선택되거나 포커스되면 색이 생기는데, 그때 요소가 1px 밀리지 않게 미리 자리를 잡아두는 것이다. 흔한 기법이다.

결정 — 두께 훅을 여기에도 적용한다. 오히려 적용하지 않으면 위험하다 — 소비자가 두께를 2px로 바꿨을 때 보이는 테두리만 2px이 되고 이 자리는 1px로 남아 선택 시 요소가 밀린다.

함정 ④ box-shadow 로 그린 테두리가 있다

_select.scss:206   box-shadow: inset 0 0 0 var(--nui-border-width) …;

border 가 아니라 안쪽 그림자로 테두리를 흉내낸 자리다. (레이아웃을 밀지 않으려고 이렇게 쓴다.) 결정 — 여기도 같은 훅을 쓴다. 소비자 눈에는 똑같은 "테두리"이므로 한 값으로 움직여야 한다.
