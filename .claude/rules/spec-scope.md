# Spec 규율 — 무엇(What) / 어떻게(How) 의 경계

spec 은 `.claude/specs/<Name>.md` 에 두고 [`_TEMPLATE.md`](../specs/_TEMPLATE.md) 서식을 따른다.
이 문서는 **spec 에 무엇을 담고, 구현이 무엇을 자율로 정하는지**의 경계를 정한다.

## 1. 원칙

> **spec 은 "무엇을 만들지"만 정의하고, 구현이 "어떻게 만들지"를 정한다.**

단 "어떻게" 중에서도 spec 에 명시적으로 적힌 것(예: "react-select 을 `unstyled` 로 감싼다")은
spec 영역으로 승격된다.

## 2. spec 영역 — 바꾸려면 spec 부터 갱신한다

| 항목 | 비고 |
| --- | --- |
| 파일 배치와 서브패스 | packaging.md 갱신 목록 8곳 |
| 공개 API (prop 이름·타입·기본값) | **받지 않는 prop 과 그 이유 포함** |
| 합성 구조 (dot notation ↔ named export) | components.md §2 |
| variant 축과 목록 | |
| 상태 정의와 **우선순위** | styles.md §7 |
| 값 소유권 (controlled / RHF) | components.md §5 |
| 동작 규칙 | 인터랙션·포커스·개폐 조건 |
| 접근성 계약 | a11y.md |
| 외부 라이브러리와 dep/peer 판정 | packaging.md |
| 스타일 분류·너비·공개 훅·**매트릭스 예외** | design-system.md |
| 완료 조건 / 주요 위험 / 제외 범위 | |

## 3. 구현 자율 영역 — spec 갱신 불필요

| 항목 | 이유 |
| --- | --- |
| 내부 div/span 마크업 골격 | Area Map 은 의미 단위. 태그 선택은 구현 책임 |
| 클래스 조립 방식 (`cn()` 사용법 등) | 결과가 spec 과 같으면 자율 |
| 내부 상태 변수명·훅 선택 | |
| 이벤트 핸들러 함수명 | |
| **매트릭스가 정한 토큰** | design-system.md 를 따르면 되므로 spec 에 다시 쓰지 않는다 |

## 4. spec 을 이탈하면 spec 을 고친다

구현 중 더 나은 방식을 찾아 **§2 영역**을 벗어나면, 임의로 두지 말고 spec 을 실제 구현에
맞게 **갱신**한다(무엇을 왜 바꿨는지 한 줄). §3 자율 영역은 갱신이 불필요하다.

## 5. spec 에는 **현행만** 남긴다 — 이력 누적 금지 ★

spec 은 "지금 이 컴포넌트가 **무엇인지**"의 단일 출처다. **"무엇이었는지"는 담지 않는다.**
이력은 Git 히스토리에 있다. §4 의 "갱신한다"는 **추가가 아니라 교체**다.

- 검증 결과를 날짜별 블록으로 **덧붙이지 않는다.** 덮어쓴다
- 판단 근거로 꼭 남겨야 하는 과거 항목은 첫 줄에 `SUPERSEDED (YYYY-MM-DD)` 를 붙인다.
  **표기 없는 과거 기록은 두지 않는다**
- **자기 작업만으로는 갱신되지 않는 값을 적지 않는다.** 전역 수치(전체 페이지 수, 전체
  테스트 건수)를 적으면 **다른 컴포넌트 작업만으로 낡아** 손대지 않은 spec 이 틀린 상태가
  된다. 그 컴포넌트가 소유한 것만 남긴다. 검증 수치는 spec 이 아니라 검수 보고가 담는다

### 5-1. Open Questions 는 살아 있는 절이다 ★

`§13 Open Questions` 는 **구현만으로는 의도인지 판단할 수 없는 것**을 모아두는 자리다.
놓친 결정을 드러내는 장치이므로 비워두려 애쓰지 않는다.

| 시점 | 할 일 |
| --- | --- |
| spec 작성 / 역추출 | 판단 불가한 것을 질문으로 남긴다 |
| **검증·검수 단계** | 새로 발견되면 **추가한다** |
| 결정되면 | **항목을 지운다.** 결정 내용은 spec 본문(해당 절)에 반영한다 |

- 답이 나온 항목을 "해결됨 ✅" 으로 **남겨두지 않는다.** 지운다
- 결정이 코드를 바꿨으면 본문과 코드를 함께 고친다. Open Question 만 지우면
  spec 과 구현이 어긋난다
- **breaking 여부를 함께 적는다.** 공개 API 를 닫는 것과 여는 것은 비용이 다르다 —
  막았다 여는 건 non-breaking, 열었다 닫는 건 breaking 이다

## 6. 언제 spec 을 쓰나

| 상황 | spec |
| --- | --- |
| 신규 컴포넌트 | **구현 전에** 작성하고 합의한다 |
| 이식 | 구현 후 역추출해도 된다. 구현이 정본이다 |
| 공개 API 변경 | 구현 전에 spec 을 먼저 고친다 |
| 시각만 변경 | §9 스타일 절을 갱신한다 |
| 내부 리팩터 | 갱신 불필요 |
